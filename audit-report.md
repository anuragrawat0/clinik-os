# Clinik OS audit — M0 through M1b (master `c32e772`)

Audit date: 2026-11-28. Scope: everything on `master` at `c32e772fda570c32995917afd1104a8032308417`.
Method: code reading, the existing suites, new failing tests, and live checks against the owner's Compose stack at http://127.0.0.1:3000 using the test platform-admin account (credentials masked). Live data was created only in organizations whose slug starts with `audit-`.

Live-stack notes that affect how to read this report:

- When the audit started, `api`, `web` and `worker` were not running. When they were first started, the images were stale: built 2026-11-26 03:38 IST, before `be56d43` and `c32e772`. For example, that build had no `Referrer-Policy` header config. The owner rebuilt, and every live result below is from images built 2026-11-28 00:50 IST from master.
- The owner's local `.env` had `SMTP_HOST=127.0.0.1` (`.env.example` uses `mailpit`). Inside the API container that is its own loopback, so every invitation and password-reset email failed (`emailDelivery: "failed"`). The owner switched it to `mailpit` and recreated `api`. The live WF-1-style run (§3.4) ran after that fix (run id `986bf8`, org `audit-opus-986bf8`; an earlier org `audit-opus-1` was also created).

## 1. Summary

| Severity | Count                                                           |
| -------- | --------------------------------------------------------------- |
| Blocker  | 1                                                               |
| Major    | 5                                                               |
| Minor    | 16 (one of them, m-4, is a refuted concern kept for the record) |

Top 5:

1. **B-1 (blocker): any org owner can hang the whole API, for every tenant, with about 10 parallel wrong-password ownership-transfer requests.** The denial path opens a second pool connection while the request's tenant transaction holds the first. The pool has `max: 10` and no acquire timeout. Proven by a new test: after 20 s, 12 requests were still pending and Postgres showed 10 `idle in transaction` backends. Only a restart recovers.
2. **M-1: no security headers.** There is no CSP, no `frame-ancestors`/`X-Frame-Options`, no `nosniff`, and `X-Powered-By: Express` / `Next.js` are sent. ARCHITECTURE §7 requires Helmet. The login form renders and is clickable inside a cross-origin iframe (verified live).
3. **M-2: `Asia/Kolkata` is rejected as `INVALID_TIMEZONE`.** It is the canonical IANA zone for India, and this is an INR product. Node 22's `Intl.supportedValuesOf('timeZone')` returns legacy aliases (`Asia/Calcutta`, `Europe/Kiev`), so canonical names fail at the API. M2 builds the slot engine on branch timezones.
4. **M-3: a removed member's pending invitations still work.** An org admin invites people, is removed, and the invitations can still be accepted afterwards (new test: 204, expected 404). Demotion has the same gap.
5. **M-4: unexpected 500s are never logged with a cause.** `ProblemDetailsFilter` swallows the exception, and pino-http logs only "failed with status code 500". The same pattern (`catch {}`) hid the SMTP misconfiguration: the log says only "An authentication email could not be sent."

Verdict: **FIX FIRST**. Blocker B-1 must be fixed before M2. See §6.

## 3. PART B — Findings (most severe first)

### Blocker

**B-1. Ownership-transfer denials deadlock the connection pool → API-wide outage**

- Where: `apps/api/src/modules/tenancy/member.service.ts:240-241, 308-356` (`audit.record(...)` and `sessions.revoke(...)` without `tx`); `apps/api/src/core/db/database.module.ts:465-469` (`max: 10`, no `connectionTimeoutMillis`); `core/access/access.module.ts:81` (the tenant transaction holds a connection for the whole request).
- Repro (test, not run live because it would hang the owner's API): as any org owner, send 10+ concurrent `POST /api/v1/orgs/:orgId/ownership-transfer` with a wrong `currentPassword`. Each request holds one pooled connection in its tenant transaction. The first denial then asks the pool for an 11th connection to write `org.ownership_transfer.denied`, and the others queue behind it on `pendingReauthDenials`. Nothing is ever released. `/health`, login and every other tenant's requests then hang forever.
- Evidence: `apps/api/test/audit/m1-audit.e2e.spec.ts` › "answers 12 concurrent wrong-password transfers…" fails: `TIMEOUT` after 20 s, and `pg_stat_activity` showed `[{"state":"idle in transaction","count":10}]`. The suite's `afterAll` then times out too, because `app.close()` cannot drain the pool.
- Why missed: the slice-2 tests exercise denials one at a time and serially. The "pool-connection residual" was recorded as theoretical and not tested under concurrency. No pool acquire timeout exists to turn the deadlock into an error.
- Fix: (a) write the denial audit and revoke **after** the tenant transaction ends. Throw a typed error and let the interceptor run an `afterRollback` callback, or reuse `afterCommit`-style hooks for the failure path. Or (b) reserve a dedicated small pool (`max: 2`) for out-of-band audit writes. In all cases, set `connectionTimeoutMillis` (e.g. 5 s) and `idle_in_transaction_session_timeout` on `clinic_app`, so any future second-connection bug fails a request instead of the process. Also cap concurrent reauth attempts per session: reject while one is pending, instead of queueing.

### Major

**M-1. No security headers; login is frameable; framework banners sent**

- Where: `apps/api/src/http-app.ts` (no Helmet, `x-powered-by` enabled); `apps/web/next.config.ts:7-12` (only `Referrer-Policy` on three pages; `poweredByHeader` not disabled).
- Repro (live): `curl -sD- http://127.0.0.1:3000/login` shows `X-Powered-By: Next.js` and no CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy or Permissions-Policy. `curl -sD- …/api/v1/health` shows `x-powered-by: Express`. From `http://localhost:4444` an `<iframe src="http://127.0.0.1:3000/login">` renders the form with "Sign in" enabled. Authenticated pages bounced to login in the frame only because the cross-site frame carries no `SameSite=Lax` cookie. A same-site origin (sibling subdomain when deployed) would get the cookie and could clickjack Remove/Transfer.
- HSTS: absent. Expected on http localhost; it must be on wherever TLS terminates.
- Why missed: ARCH §7 lists Helmet, but there is no test, and the reviews read the design as if it were the implementation.
- Fix: in Next `headers()`, for `/:path*`, set `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'` (plus the nonce or `'unsafe-inline'` that Next needs), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin` (keep `no-referrer` on the token pages) and `Permissions-Policy: camera=(), microphone=(), geolocation=()`. M4 adds Daily, which needs `camera=(self)`. Also set `poweredByHeader: false`. API: `app.getHttpAdapter().getInstance().disable('x-powered-by')` and `nosniff`.
- Tests: `apps/web/test/audit/security-headers.spec.ts` (8 failing), `apps/api/test/audit/m1-audit.e2e.spec.ts` › headers (failing).

**M-2. Canonical IANA timezones rejected (`Asia/Kolkata`, `Europe/Kyiv`, `Asia/Ho_Chi_Minh`)**

- Where: `apps/api/src/modules/tenancy/tenancy.dto.ts:16` (`new Set(['UTC', ...Intl.supportedValuesOf('timeZone')])`); `apps/web/src/features/m1/ui.tsx:43` (same list in the browser).
- Repro (live): `POST /api/v1/admin/organizations {"name":"x","slug":"audit-x","defaultTimezone":"Asia/Kolkata"}` → `422 INVALID_TIMEZONE`. In Node 22.19/22.23 (ICU 77), `supportedValuesOf` contains `Asia/Calcutta`, not `Asia/Kolkata`, and contains neither `UTC` nor `Etc/UTC`. The UI dropdown lists whatever the _browser's_ ICU returns, so a browser whose list contains `Asia/Kolkata` produces a value the server rejects, while Chrome users silently store the deprecated alias.
- Why missed: tests use `UTC` and a couple of US/EU zones that happen to be in both lists.
- Fix: validate with `try { new Intl.DateTimeFormat('en', { timeZone: v }) }` (accepts every IANA name and alias). Store the canonical form (`Intl.DateTimeFormat(…).resolvedOptions().timeZone` may return the alias, so keep the input or map it with a small alias table). Serve the dropdown list from the API so the UI and server agree.
- Test to add: `createBranch` with `Asia/Kolkata` returns 201.

**M-3. Pending invitations survive the inviter's removal or demotion**

- Where: `apps/api/src/modules/tenancy/member.service.ts:196-224` (remove does not touch `invitations`); `invitation.service.ts:389-552` (accept never re-checks that `invited_by` is still an active member able to grant the role).
- Repro: `apps/api/test/audit/m1-audit.e2e.spec.ts` › "cannot be accepted after the inviter is removed": an org admin invites a branch manager, the owner removes the admin, and the invitee accepts → **204** (expected 404). The new member's role row records `created_by` = the removed admin.
- Impact: a departing or compromised admin can pre-issue 7-day invitations (to themselves under another email, or to accomplices) that outlive removal. Same for demotion.
- Why missed: D29 was specified in terms of the removed member's own access. Invitation tests cover revoke/expiry/accept races, not inviter lifecycle.
- Fix: in `remove` (and in `replaceRoles` when grant power shrinks), revoke the target's pending invitations in the same transaction and audit `invitation.revoked` with reason `inviter_removed`. On accept, re-check that `invited_by` is still an active member with `canGrant(role, branch)`. Owner-invitations from a platform admin are exempt.

**M-4. Unexpected errors are swallowed without a cause (500s, SMTP failures)**

- Where: `apps/api/src/core/errors/problem-details.filter.ts:229-272` (never logs); `apps/api/src/modules/notifications/auth-mailer.ts:405,424` (`catch {}` → "An authentication email could not be sent.").
- Repro: the existing suite's 500 cases log only `{"err":{"message":"failed with status code 500"}}` (from pino-http). Live: with `SMTP_HOST=127.0.0.1`, every invite returned `emailDelivery:"failed"` and the log line gave no error class or code (`ECONNREFUSED`), so the misconfiguration couldn't be diagnosed from logs.
- Why missed: PHI-in-logs caution led to logging nothing. There is no test that a 5xx produces a diagnosable log.
- Fix: in the filter, for status ≥ 500 log `{ requestId, errorClass, code: SQLSTATE|systemCode, constraint }` (no message), reusing `startup-failure.ts`'s `errorClass`. In the mailer, log `{ errorClass, systemCode, responseCode }`.
- Test: `m1-audit.e2e.spec.ts` › "logs the class of an unexpected (500) error" (failing).

**M-5. Live API outage from any client is one bug away: no pool or statement timeouts anywhere**

- Where: `database.module.ts:465` (no `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout` or `idle_in_transaction_session_timeout`); `TenantWork` keeps a transaction open while the handler awaits CPU work (argon2 in transfer, accept).
- Why separate from B-1: B-1 is one trigger. Any future handler that awaits an external call, or a second connection, inside the tenant transaction (M4 Daily, M5 Stripe; rule §3.3.4 forbids it but nothing enforces it) reproduces the outage.
- Fix: set the timeouts above (role-level `ALTER ROLE clinic_app SET idle_in_transaction_session_timeout = '15s'`, `statement_timeout = '10s'`, in a new migration). Add a health check that reports pool waiting count.
